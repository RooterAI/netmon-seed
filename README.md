# Netmon Seed — публичный пакет для VR-устройств

Публичный репозиторий с **сид-пакетом**: установщик и клиент мониторинга сети,
который поднимает VPN и раздачу интернета на ПК, к которому подключена гарнитура.

Совместимость с устройствами VR: **Meta Quest 3, Quest S (Quest 2/3S), Quest Pro**
и другие гарнитуры, работающие по Wi-Fi через точку доступа ПК. Устройство
подключается к сети хотспота и получает интернет через туннель ПК — отдельный
клиент внутри гарнитуры не нужен.

> Репозиторий не является продуктом Meta Platforms, Inc. и не связан с ней;
> Meta, Quest — товарные знаки соответствующих правообладателей. Здесь описан
> только способ подключения гарнитур к сети ПК.

## Что лежит в публичной части

| Файл | Назначение |
|---|---|
| `Install-Netmon.ps1` | установщик: скачивает пакет, проверяет SHA-256, ставит задачу автозапуска |
| `manifest.json` | версия, ссылка на файл, контрольная сумма |
| `netmon.exe` | клиент (сид): мониторинг, VPN, хотспот, диагностика |
| `README-USER.md` | короткая инструкция для конечного пользователя |

## Что выдаётся после регистрации (приватная часть)

Профили подключения, персональные конфигурации и ключи в публичный пакет
**не входят**. После оплаты и регистрации устройство забирает их из приватного
репозитория (доступ по токену) или с самого сервера по SSH/git.

## Быстрый старт

```powershell
# 1. скачать установщик
irm https://raw.githubusercontent.com/<owner>/netmon-seed/main/public/Install-Netmon.ps1 -OutFile Install-Netmon.ps1

# 2. установить (нужен запуск от администратора)
powershell -ExecutionPolicy Bypass -File .\Install-Netmon.ps1
```

Установщик кладёт клиент в `C:\Program Files\netmon`, создаёт задачу
планировщика `netmon` (запуск при входе, наивысшие права) и запускает клиент.

## Что нового в 3.6.0

**Один переключатель режимов сети: 
etmon.exe --cli mode.**

`
netmon.exe --cli mode            # что сейчас и что есть
netmon.exe --cli mode direct     # DHCP от роутера, ничего не меняем (база)
netmon.exe --cli mode proxy      # системный прокси на своё ядро (любой протокол)
netmon.exe --cli mode vpn        # встроенный VPN Windows (весь трафик, включая UDP)
`

* Каждый переход сначала подтверждает рабочий выход в сеть, и только потом
  считается включённым. Не подтвердился — монитор откатывается к обычному режиму
  и говорит об этом.
* Смена режима начинается с чистого листа: снимаются следы предыдущего (прокси от
  ядра поверх VPN и наоборот).
* Новая проверка «Режим сети»: показывает текущий режим и подтверждённый выход.
* Проверки перестали пугать в обычном режиме: в direct отсутствие TUN, клиента и
  маршрута через тоннель — норма (информационные строки), а в pn те же строки
  становятся ошибкой. SOCKS-вход проверяется на порту своего ядра, а не на
  оставшемся от прежнего клиента 2080.
* Общий статус в direct и proxy — «ок» на рабочей сети (раньше был «сбой»).

Проверено: direct → proxy → direct → vpn → direct, каждый переход с проверкой;
через ядро 95.181.173.61, напрямую 185.191.59.120.
## Что нового в 3.5.3

**Монитор замечает, что сломал сеть, и откатывается сам.**

* Включение транспорта больше не начинается с прокси: сначала ядро должно
  **реально выпустить** запрос. Не вышло — перебираются профили, выбирается
  рабочий; если рабочих нет, транспорт не включается, сеть остаётся как была.
* Все проверки здоровья стали сквозными: не «порт 22080 слушается», а «трафик
  через ядро проходит». Раньше ядро могло слушать и не иметь выхода — прокси
  оставался включённым, и интернета не было нигде.
* Быстрый сторож (в окне, раз в 20 с), предохранитель (каждые 10 с) и задача
  `netmon-proxy-guard` (раз в минуту) при провале проверки снимают прокси и
  сбрасывают желаемое состояние — система возвращается к DHCP-режиму.
* `guard-install` работает и из консоли: задача ставится из окна, у которого
  есть права.

Проверено: при живом ядре и «мёртвом» профиле (порт открыт, выхода нет) прокси
снимается автоматически за ~30 с, `curl` напрямую снова отдаёт адрес
провайдера — без участия человека.

## Что нового в 3.3.0

**Самообновление без разрыва сети.** Монитор больше не нужно останавливать и
запускать вручную при выходе новой версии.

* `netmon.exe --cli update apply` (и ключ окна `update-apply`) скачивают новый
  файл, сверяют SHA-256, кладут его рядом как `netmon.exe.new` и запускают
  **обновлятор** — отдельную копию себя в `%TEMP%`.
* Обновлятор ждёт завершения старого монитора, отодвигает старый exe в `.old`,
  ставит новый на его место и запускает новую версию, затем убирает `.old`.
* Выход для обновления **не трогает сеть**: ядро и системный прокси продолжают
  работать, поэтому туннель не рвётся ни на секунду — новый экземпляр просто
  подхватывает уже поднятое ядро.
* Автопроверка: `update_mode=auto` в `netmon.ini` — монитор раз в час смотрит
  манифест и, если версия новее, применяет обновление сам.
* Журнал обновлений: `config\netmon\update.log`.

Важно: сборки до 3.3.0 такого механизма не имеют — их нужно один раз перевести
на 3.3.0 вручную. Дальше обновления идут сами.

## Что нового в 3.2.0

Главное: **выход из монитора больше не оставляет сеть без интернета**.

* Перед закрытием окно возвращает систему в исходное состояние (системный прокси
  снят, ядро остановлено), затем **проверяет сеть** (DNS + TCP + настоящий
  HTTPS-запрос) и только после этого завершается. Если сеть не поднялась —
  выключить прокси полностью, сбросить кэш DNS и проверить снова; если и это не
  помогло, монитор остаётся работать, чтобы не оставить пользователя без сети.
* Сторож прокси: задача планировщика `netmon-proxy-guard` раз в минуту проверяет,
  что прокси не указывает на мёртвое ядро, и снимает его. Чинит сеть даже после
  жёсткого убийства процесса и после перезагрузки.
* Предохранитель: отдельный процесс следит за портом ядра и за 3 секунды
  возвращает системные настройки, если ядро пропало.
* Ядро запускается с `CREATE_BREAKAWAY_FROM_JOB`: завершение задачи планировщика
  или дерева процессов монитора больше не убивает туннель, сеть остаётся рабочей.
* При старте монитор самолечится: если системный прокси остался от аварии, он
  либо поднимает транспорт (если так и было задумано), либо возвращает обычный
  режим.
* `netmon.exe --cli action exit` — штатный выход из консоли тем же путём.

Проверено на живой системе: `transport on` → выход → `ProxyEnable=0`,
`ProxyServer` пуст, процессов `netmon` нет, `curl` даёт адрес провайдера;
убийство ядра → через несколько секунд прокси снят и сеть восстановлена
(запись в `transport-guard.log`).

## Что нового в 3.1.1

Проверки перестали считать «плохим» нормальный режим, когда весь трафик идёт в
наш туннель:

* «Клиент VPN» — зелёная, если туннель держит встроенный VPN Windows (сторонних
  процессов нет);
* «Маршрут по умолчанию» понимает адаптер `netmon SSTP`, а не только TUN;
* «Шлюз провайдера» и «Выход (SOCKS)» при включённом туннеле/выключенном ядре —
  информационные строки, а не ошибки;
* HTTP-пробы при выключенном SOCKS-ядре повторяются по системному маршруту
  (то есть через туннель), поэтому не показывают ложный сбой;
* «Сторож сервиса» показывает «наш сторож», «Самодостаточность» — что TUN
  поднимает встроенный VPN;
* журнал клиента больше не сыплет ошибками, когда прежний клиент не запущен:
  читается журнал нашего ядра.

## Что нового в 3.11.0

Ключевое: **раздельные маршруты с живым контролем качества** — интернет всегда есть,
а VPN используется там, где он действительно нужен.

* Правила «ресурс + участник → путь»: домен, `*.домен`, IPv4/CIDR, зоны
  (`zone:ru`, `zone:cn`, `zone:com`…) и отдельные устройства хотспота по IP.
  Путь: `direct`, `vpn` или `auto`.
* `auto` проверяет не «порт открыт», а реальную работу ресурса: DNS → TCP →
  настоящий HTTPS-ответ → отклик, джиттер, потери. Порог: потери > 15 %,
  джиттер > 80 мс, отклик > 400 мс. Решение кэшируется на 5 минут; при отказе
  прямого пути ресурс сразу уходит в VPN.
* Гео-зоны: TLD + списки CIDR (`config\netmon\zone-cn.txt`, команда
  `route zone-add cn 39.156.0.0/16`) — так `baidu.com` c TLD `.com` попадает в `cn`.
* Всё исполняется в нашем ядре на каждом CONNECT (SOCKS5 и HTTP-прокси), поэтому
  правила действуют и для устройств хотспота; адрес устройства берётся из соединения.
* CLI: `route list | add | del | default | test | quality | decide | zone-add`.
* Новая страница **«Маршруты» (Ctrl+9)**: путь по умолчанию, пресеты (YouTube,
  zone:cn, zone:ru, очистка), таблица правил с переключением пути по щелчку и
  живое качество по зонам (отклик/джиттер/потери для direct и VPN).

Проверено: `example.com → direct` через ядро — 200 за 0.10 с; `baidu.com` по
`zone:cn → vpn` — 200 за 1.16 с; YouTube по `auto` — сам перешёл на VPN, когда
прямой путь перестал отдавать ответ, и вернул 200.

## Что нового в 3.10.1

Ключевое: **монитор сам замечает новый адрес провайдера и авторизует его**, а все
процессы, которые он запускает, видны списком.

* Провайдер меняет публичный адрес несколько раз в сутки — после этого сервер
  перестаёт пускать VPN-порты. Теперь монитор в медленном цикле сравнивает
  видимый адрес с сохранённым, проверяет SSH и сам синхронизирует вайтлист
  (один раз на адрес, не чаще раза в 10 минут). В журнале: «адрес 83.137.54.30
  авторизован на сервере».
* Авторизация открывает **все** входы — 443, 8388, 8443, 8444, 8447, 8448 (tcp,
  а где нужно и udp), — и не только текущий адрес, но и его подсеть `/24`:
  провайдер меняет адрес несколько раз в сутки внутри своей сети, поэтому
  точечное правило ломалось при следующей смене. Проверено: после авто-авторизации
  работают все 5 профилей (было 3), и смена адреса внутри подсети VPN не ломает.
* Новая страница **«Процессы» (Ctrl+8)**: роль, процесс, pid, память, время
  запуска, путь к журналу. Видны монитор, ядро (`core run`), предохранитель,
  сторож-задача, терминалы PowerShell и CMD, обновлятор, воркер саморазработки и
  все найденные потомки (`conhost`, `ssh`, `netsh` …). Щелчок по строке показывает
  вывод процесса во вкладке «консоль».
* CLI: `netmon.exe --cli procs` и `netmon.exe --cli procs log <pid>` — то же в тексте.
* Список чистится сам: короткоживущие роли хранятся одной записью, завершённые —
  только последние, поэтому минута за минутой список не разрастается.

## Что нового в 3.9.1

Всё выполняется во встроенных вкладках — окон на рабочем столе больше нет.

* Убрана главная причина всплывающих окон: `netmon.exe --cli` вызывал

  запусками сторожа — 0 новых консольных окон.
* Вкладки терминала: **PowerShell** и **CMD** (палитра «Терминал: новая вкладка
  CMD/PowerShell»), у CMD своё приглашение `c:\путь>`.
* Исправлено «залипание» терминала на ConPTY: после первой команды вкладка
  оставалась в состоянии «выполняется» (чтение псевдоконсоли блокировалось
  навсегда) — теперь чтение неблокирующее, завершение процесса определяется по
  его дескриптору, серия команд подряд работает.
* Кодировка вывода: `chcp 65001` и UTF-8 (pwsh при наличии), плюс выбор
  кодировки по содержимому строки — кириллица больше не превращается в «СЃРєСЂРёРїС‚».

## Что нового в 3.9.0

Ключевое: **никаких внешних окон — всё в терминале монитора**. Терминал панели
переведён на настоящую псевдоконсоль Windows (ConPTY):

* Любой консольный процесс внутри терминала (`netsh`, `git`, `python`, `cmd`,
  собственные скрипты) видит консоль и больше **не открывает своё окно** — вывод
  идёт во вкладку терминала. Раньше терминал работал на трубах без консоли, и
  Windows создавала каждому дочернему процессу новое окно.
* `Ctrl+C` в терминале теперь прерывает по-настоящему: символ уходит в
  псевдоконсоль, PowerShell успевает прибрать за собой, затем срабатывает
  job-объект (всё дерево процессов).
* Команды из CLI выполняются в терминале монитора: `netmon.exe --cli cmd
  "term-run=<команда>"` — состояние командной строки (приглашение, вывод, код
  возврата) видно в панели.
* Скрипты, которые монитор выполняет сам (исправления от DeepSeek, сборка
  саморазработки), попадают во вкладку «консоль»: команда, код возврата и первые
  40 строк вывода.
* Внешние окна остаются только там, где это технически необходимо: редактор
  конфигов, папка с логами, браузер (ссылки), запрос прав администратора (UAC).

Проверено: `netsh interface ipv4 show interfaces` и `netstat -an` внутри терминала
монитора — вывод в панели, количество окон на рабочем столе не изменилось (7 → 7).

## Что нового в 3.8.0

Ключевое: **контроль пакетов на шлюзе и сторонних приложений**. Сеть проверяется не
только со стороны ПК, но и на сервере, а восстановление доводится до конца.

* `netcheck server` — состояние шлюза за окно 4 с: байты и пакеты, ошибки и дропы
  интерфейса, TCP-ретрансмиты, число соединений, MTU, пинг шлюза до 1.1.1.1.
  Вердикт: ошибки интерфейса — сбой, дропы — до 0.2 % пакетов, ретрансмиты — до
  эталон + 5 %. `netcheck server-baseline` запоминает норму.
* `netcheck full` — всё сразу: клиентские метрики, пики, скорость с эталоном, шлюз,
  конкуренты; один вердикт.
* `netcheck silence` — крайняя мера: гасит сторонние клиенты (nekoray, sing-box,
  clash, wireguard, openvpn…) и отключает чужие задачи-сторожа. Используется
  автоматически, когда после снятия нашего прокси сеть так и не поднялась.
* Состояние задач-сторожей теперь читается из XML (`<Enabled>`), а не из
  локализованного текста `/FO LIST` — раньше в русской системе выключенные задачи
  выглядели включёнными, и сторож «отключал» их повторно каждый запуск.
* Пики: одиночная медленная проба больше не считается сбоем (в эталон пишется
  `peak_https`), но при многократном росте пика вердикт становится «перегрузка».
* Новая страница **«Сеть» (Ctrl+7)**: тот же отчёт, что `netcheck full` — метрики с
  допусками, скорость с эталоном, шлюз, конкуренты. Кнопки: «Проверить всё»,
  «Эталон сети», «Проверить шлюз», «Погасить конкурентов».
* Новая проверка самодиагностики «Пакеты на шлюзе».

Проверено на живой системе: убийство всех процессов монитора в режиме `proxy` →
ядро поднято и окно возвращено за 13 секунд, `netcheck full` — «сеть полностью в
норме» (0 ошибок, 0 дропов на 316 пакетов, 0 % ретрансмитов, MTU 1500).

## Что нового в 3.7.2

Ключевое: **сеть не пропадает никогда**. Раньше сторож проверял только «порт
открыт», а задача-сторож удалялась при выключении транспорта — после падения всех
процессов монитора сеть могла остаться с прокси на мёртвый порт. Теперь:

* Задача `netmon-proxy-guard` ставится при **каждом** старте монитора и не
  удаляется при выключении транспорта, поэтому сеть возвращается даже если
  монитор убили вместе с ядром (проверено: убийство всех процессов в режиме
  `proxy` → через 8 секунд ядро поднято, порт отвечает, монитор восстановлен).
* Сторож больше не полагается на счётчики в памяти (задача — новый процесс каждую
  минуту): подтверждение и решение принимаются внутри одного запуска.
* Новый модуль `netcheck`: реальные метрики (DNS, TCP, HTTPS, ICMP, джиттер,
  потери, внешний адрес, загрузка CPU), эталон **на каждый режим**, допуски с
  учётом шума и нагрузки, вердикт `ok/хуже`.
* После восстановления сети сторож проверяет метрики и при расхождении
  **откатывается** к обычному режиму и проверяет снова; в журналах
  `netcheck.log` и `transport-guard.log` видно, что именно было не так.
* `netcheck rivals` показывает, что ещё влияет на сеть: чужой WinHTTP-прокси,
  туннельные адаптеры в маршруте по умолчанию, сторонние клиенты, чужие задачи.
* `netcheck speed` — короткий замер скорости (2 МБ в текущем режиме): «страница
  открылась» и «канал работает» — разные вещи (проверено: 119 Мбит/с напрямую,
  10.5 Мбит/с через ядро).
* CLI и GUI дублируют друг друга: `netcheck [baseline|verify|rivals|speed]` и карточка
  «Качество сети» на странице «Подключение» (Ctrl+6) с кнопками «Проверить
  метрики» и «Сделать эталоном»; в самодиагностике появилась проверка `netcheck`.

## Что нового в 3.0.0

Ключевое: **свой VPN вместо чужого клиента**. Монитор поднимает штатное
подключение Windows (`WAN Miniport (SSTP)`) через RAS API — сторонние клиенты и
драйверы больше не нужны, весь трафик, включая UDP, идёт в туннель.

* Серверная половина — наш собственный эндпоинт `server/netmon_sstp.py`:
  TLS → HTTP `SSTP_DUPLEX_POST` → кадры SSTP (бит `C`, Crypto Binding с nonce и
  SHA-256 сертификата) → PPP (LCP, CHAP-MD5, IPCP) → Linux TUN + NAT.
* Клиентская половина — `vpn.cpp` на `rasapi32`: создание подключения
  (`RasSetEntryProperties`), учётные данные, `RasDial`, `RasHangUp`,
  `RasDeleteEntry`, доверие сертификату, `vpn repair` для ошибки 756.
* Новая проверка «Встроенный VPN» и кнопки подключения/отключения/починки в
  карточке проверки.
* Поддержан `WAN Miniport (SSTP)` как TUN-адаптер: маршрут по умолчанию идёт
  через туннель, локальная сеть остаётся доступной.

Проверено на живой Windows 11: `vpn on` → `10.77.0.3`, `curl https://api.ipify.org`
без прокси отдаёт адрес сервера, DNS и UDP идут через туннель, а с процессами
прежнего клиента, остановленными, интернет продолжает работать — то есть замещение
действительно полное. Версия базы знаний: статья «Встроенный VPN без сторонних
клиентов».

## Обновления

Клиент сам проверяет `manifest.json` (режим `update_mode` в `netmon.ini`):

```powershell
netmon.exe --cli update check     # есть ли новая версия
netmon.exe --cli update apply     # скачать, проверить SHA-256, подменить и перезапуститься
netmon.exe --cli self             # версия, права, автозапуск, журнал
```

Версия задана в одном месте исходников (`src\version.h`), поэтому манифест и клиент
всегда согласованы: `publish.ps1` берёт номер из `netmon.exe --cli self`.

## Сборка и публикация

```powershell
powershell -ExecutionPolicy Bypass -File .\publish.ps1 -Version 2.5.2 -Push
```

`publish.ps1` копирует свежий `netmon.exe` в `public/`, считает SHA-256,
переписывает `manifest.json` и делает коммит; с `-Push` отправляет в GitHub.
