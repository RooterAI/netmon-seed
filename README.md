# Netmon Seed — публичный пакет для VR-устройств

Публичный репозиторий с **сид-пакетом**: установщик и клиент мониторинга сети,
который поднимает VPN и раздачу интернета на ПК, к которому подключена гарнитура.

Совместимость с устройствами VR: **Meta Quest 3, Quest S (Quest 2/3S), Quest Pro**
и другие гарнитуры, работающие по Wi-Fi через точку доступа ПК. Устройство
подключается к сети хотспота и получает интернет через туннель ПК — отдельный
клиент внутри гарнитуры не нужен.

> Репозиторий не является продуктом Meta Platforms, Inc. и не связан с ней;
> Meta, Quest — товарные знаки соответствующих правообладателей. Здесь описан
> только способ подключения гарнитур к сети ПК.

## Что лежит в публичной части

| Файл | Назначение |
|---|---|
| `Install-Netmon.ps1` | установщик: скачивает пакет, проверяет SHA-256, ставит задачу автозапуска |
| `manifest.json` | версия, ссылка на файл, контрольная сумма |
| `netmon.exe` | клиент (сид): мониторинг, VPN, хотспот, диагностика |
| `README-USER.md` | короткая инструкция для конечного пользователя |

## Что выдаётся после регистрации (приватная часть)

Профили подключения, персональные конфигурации и ключи в публичный пакет
**не входят**. После оплаты и регистрации устройство забирает их из приватного
репозитория (доступ по токену) или с самого сервера по SSH/git.

## Быстрый старт

```powershell
# 1. скачать установщик
irm https://raw.githubusercontent.com/<owner>/netmon-seed/main/public/Install-Netmon.ps1 -OutFile Install-Netmon.ps1

# 2. установить (нужен запуск от администратора)
powershell -ExecutionPolicy Bypass -File .\Install-Netmon.ps1
```

Установщик кладёт клиент в `C:\Program Files\netmon`, создаёт задачу
планировщика `netmon` (запуск при входе, наивысшие права) и запускает клиент.

## Что нового в 3.20.7

**Гонка путей, кэш DNS, накопленная статистика по хостам и числа вместо
ощущений.**

Разбор узких мест «первого байта» и решения по внешнему разбору качества:

* **Гонка путей (happy eyeballs).** Прямой путь и туннель стартуют одновременно
  (второй — через 75 мс, чтобы не тратить ресурсы зря). Первые 250–400 мс
  отдаём предпочтение пути по правилу, дальше выигрывает тот, кто реально
  установил TCP. Раньше опрос был последовательным: если прямой тормозил
  320 мс, приложение ждало ещё 400 мс туннеля, хотя туннель был готов раньше.
* **Найден и исправлен источник «сайт иногда открывается 3–4 секунды».** Заход,
  проигравший гонку, отменялся через join() — а он висел на своём таймауте
  (до 4 с), и именно это время попадало в ответ приложению. Теперь состояние
  захода живёт на куче и удерживается shared_ptr, поток отцепляется, сокет
  закрывается сам.
* **Размыкатель туннеля больше не срабатывает на потерю пакета.** Раньше любой
  обрыв рукопожатия запрещал туннель на 3 секунды, и следующий запрос мгновенно
  получал 502 (на замерах — 3 из 10 отказов на Instagram). Теперь размыкатель
  ставится только если ядро не отвечает вообще, а заход в туннель повторяется
  до трёх раз через 150 мс: провайдер выбрасывает часть датаграмм, второй заход
  обычно проходит.
* **Кэш DNS (64 % попаданий)** и **кэш исходящего интерфейса (5 с)**: имена
  больше не разрешаются на каждое соединение, а перебор адаптеров и таблицы
  маршрутов (5–15 мс) не выполняется на каждое соединение.
* **Накопленная статистика по хостам (EWMA)** в outes-ewma.ini: сглаженные
  времена обоих путей и потери. Один медленный замер больше не переключает
  сайт: уход в туннель только при подтверждении статистикой, а прямой путь
  уводится из-под хоста лишь после **двух сбоев подряд**. Медленное окно линии
  (все три замера плохие) перепроверяется через 200 мс.
* **Метрики вместо ощущений**: 
etmon.exe --cli transport-metrics — первый
  байт от цели (средний/худший, по хостам), победы путей в гонке, попадания в
  кэш DNS, отказы; журнал config\netmon\transport-metrics.jsonl (строка в
  минуту). Счётчики conn_resets_on_path_switch и path_switches_mid_conn
  структурно равны нулю: решение принимается один раз на соединение.
* **Серверная сторона линии**: на VPS включены **BBR** и q (вместо cubic),
  TCP Fast Open = 3 — меньше зависимости от потерь и на один round-trip меньше
  на повторных соединениях.
* Сокеты шлюза: SO_KEEPALIVE с зондами (20 с простой, далее 3 с), TCP_NODELAY
  на всех ногах; буферы сокетов не фиксируются — автоподстройка ядра работает
  лучше констант.

Итог замера (агрессивные окна провайдера, scripts/Test-WebPaths.ps1):
YouTube/Facebook/Instagram/Gemini — **0 % отказов**, 0,57–0,81 с через туннель
(напрямую 100 % отказов); повторная серия 10 запросов к Instagram — 10/10
успешно; ЦИАН и Маркет напрямую 0,05–0,17 с. Простой клиента — 6,3 % ядра
на все процессы, память 161 МБ.

Сознательно не делали сейчас: TLS-resumption на стороне шлюза (для CONNECT
сессию возобновляет браузер, нам там нечего кэшировать) и полный прозрачный
failover посреди соединения (нужен буфер неподтверждённых данных и повтор
рукопожатия на другом пути — это следующий слой, поверх уже измеренного
качества).
## Что нового в 3.20.6

**Разделение путей: заблокированное — через туннель, доступное — напрямую, с
проверкой на реальных сайтах.**

Проверили рабочий режим на живых страницах (YouTube, Gemini, Facebook,
Instagram, Яндекс, Маркет, Ozon, ЦИАН, DeepSeek) — и нашли, что решение
«прямо или через туннель» принималось по испорченным данным:

* в «отклик» попадало время DNS (у задушенного резолвера — до 2 с), поэтому
  российские сайты с откликом 30–60 мс выглядели «плохим путём» и уходили в
  туннель: Маркет открывался 0,86 с вместо 0,09 с, Ozon — 0,86 против 0,06 с.
  Теперь имя разрешается один раз, замеряется только соединение;
* путь выбирается **сравнением двух путей в одной пробе** (минимум из замеров,
  а не среднее и не порог): при потерях среднее «плывёт», минимум устойчив;
* решение не дёргается: при разнице меньше двукратной остаётся прежний путь,
  для российской зоны нужен трёхкратный перевес, чтобы уйти в туннель;
* срок годности решения — 2 минуты вместо 5: провайдер душит короткими
  всплесками, и одна просадка больше не уводит сайт в туннель надолго;
* российская зона идёт напрямую сразу, пока фоновый замер не докажет обратное.

Итог на живых страницах (замеры scripts/Test-WebPaths.ps1 в моменты атак
провайдера): YouTube/Facebook/Instagram — 0 % отказов только через туннель
(напрямую 100 % отказов), 0,5–0,7 с на страницу; Яндекс и Маркет напрямую
0,04–0,12 с; ЦИАН 0,05 с; когда прямой путь просаживается, тот же ресурс
открывается через туннель — сайт не пропадает.

## Что нового в 3.20.5

**Системные вызовы пакетами, воркеры по числу ядер, проба клиента в 3 раза дешевле.**

* Сервер: приём ecvmmsg (до 32 датаграмм за вызов) и отправка sendmmsg (до 64).
  На высокой скорости каждый пакет отдельным sendto/ecvfrom — это 38 тыс.
  переходов в ядро в секунду.
* Насос отдаёт до 256 свежих пакетов за проход (было 96 — это и был потолок
  37 МБ/с на поток), но не больше, чем позволяет окно при измеренном минимуме
  RTT. Пейсинг по минимуму RTT, а не по сглаженному: сглаженное раздувается,
  когда подтверждение ждало починки дыры, и мы сами себя тормозили.
* Итог на петле (оба конца на одном ядре): **94 МБ/с** одним потоком и 95 МБ/с
  четырьмя, цена мегабайта **3,6–4,7 мс CPU у сервера** и ~2 мс у клиента.
  Управляемые потери (	c netem): 7 % → 5,5 МБ/с (4 потока), 3 % → 7,0,
  1 % → 15,4, без потерь → 94.
* Число воркеров теперь по ядрам: --workers 0 (по умолчанию) — один воркер на
  ядро минус одно для системы и релея, максимум 8. Прежние четыре воркера на
  одноядерном VPS просто делили одно ядро (овер-подписка); SO_REUSEPORT
  выигрывает только когда ядер действительно несколько.
* Клиент: проба монитора кэширует таблицу адресов на 10 с и список процессов на
  5 с — проход пробы подешевел со 155 до **17–19 мс**, простой клиента — до
  **8,6 % ядра**; пульс схемы рисуется только когда окно активно и курсор внутри.

## Что нового в 3.20.4

**Протокол перестал захлёбываться на потерях: 0,05 МБ/с → 5–13 МБ/с, а цена
мегабайта упала в 8–10 раз.**

Замеры на своей петле (сервер на том же хосте, провайдер не участвует) показали,
что виноват был не канал, а наш горячий путь. Профиль сервера: 58 % процессора —
обход `std::map` неподтверждённых пакетов, ещё часть — создание `EVP_CIPHER_CTX`
и HMAC-контекста на каждый пакет.

* **Сервер, горячий путь.** Окно «в полёте» стало очередью по номерам (подтверждения
  кумулятивные, номера идут подряд), повтор — это один `sendto` уже зашифрованного
  пакета. Убраны копии строк на каждый пакет (расшифровка в переиспользуемый
  буфер, HMAC прямо по принятому буферу), состояния HMAC-SHA256 (ipad/opad)
  считаются один раз на ключ, контекст AES живёт в потоке, nonce — счётчик со
  случайным префиксом вместо `RAND_bytes` на пакет, кэш повторов — таблица с
  открытой адресацией вместо `std::map`. Итог: **64,5 → 6,3 мс CPU на мегабайт**,
  пропускная способность на петле **17,5 → 49 МБ/с**.
* **Исправлен холостой цикл.** Когда очередь отправки заполнялась, сервер не читал
  целевой сокет, но уровень epoll продолжал сообщать «есть данные»: 4 млн
  пустых проходов в секунду и 88 % ядра при 0,05 МБ/с. Теперь приём выключается
  на время (`EPOLLIN` снимается) и возвращается, когда очередь разошлась.
* **Восстановление потерь переписано.** Повтор был «go-back-N на 1536 пакетов»:
  при 7 % потерь передача вставала (0,03–0,05 МБ/с). Теперь повторяется только
  «дыра» (номер `sendBase`), есть быстрое восстановление по трём одинаковым
  подтверждениям, ограничение RTO (150–600 мс вместо роста до 4 с) и **NACK**:
  получатель одним пакетом перечисляет номера, которых у него нет, а отправитель
  повторяет их сразу все, не чаще раза в RTT на пакет. Управляемые потери через
  `tc netem` на петле: **7 % → 5,3 МБ/с, 3 % → 12,7, 1 % → 25, 0 % → 42–49**.
* **Клиент.** Ключ BCrypt для AES и состояние HMAC создаются один раз (было —
  на каждый пакет, это системные вызовы в ядро CNG), XOR гаммы — словами, nonce —
  счётчик, приём — строка с курсором вместо дека байтов (приложение читало из
  дека по одному байту). На реальном канале цена мегабайта упала с 43–48 до
  13–20 мс, а в простое клиент занимает **6,9 % ядра вместо 21–25 %**: проба
  монитора кэширует дорогие системные запросы (снимок процессов, таблица
  адресов, RAS, режим сети — по 15–30 мс каждый) и не перерисовывает схему,
  когда окно не в фокусе.
* **`Measure-NetmonLoad.ps1`** больше не показывает отрицательный расход
  процессора релея (python-процессы плодят короткоживущих детей) и делает
  контрольный замер напрямую — чтобы отличить атаку провайдера от нашей цены.
  Контроль в тот же вечер: напрямую 0 байт за 22 с, через наш туннель — 10–17 МБ/с.

## Что нового в 3.20.3

**Диагностика перестала пугать ложными сбоями, а CLI — вешать окно.**

* Тяжёлые команды (`status`, `diagnose` — по 25–40 секунд проверок) больше не
  копятся в окне: выполняется ровно одна, остальные сразу получают ответ
  «занято». Раньше несколько запусков подряд блокировали канал управления, и
  консоль показывала «экземпляр netmon не ответил за 300 с», после чего проверка
  шла без прав администратора и рапортовала «SSH закрыт» → ложный «сбой».
* Проверки, которым нужны права администратора (SSH-канал, порты), без этих прав
  помечаются как «не проверялось», а не «сбой».
* «Внешний интернет» больше не привязан к одному адресу 1.1.1.1: если он не
  отвечает, но HTTPS к другим узлам проходит, это замечание с объяснением
  («провайдер режет часть адресов»), а не «интернета нет».
* Пункт «провайдер часто меняет IP» стал информационным: привязка теперь
  автоматическая, по подписи пакета.

## Что нового в 3.20.2

**Перепривязка к серверу работает сама — по подписи пакета, а не по IP.**

Провайдер меняет домашний адрес по нескольку раз в неделю, а сервер пускал
закрытые порты (443, 8388, 8443, 8444, 8447, 8448) только с известного адреса:
после каждой смены туннель отваливался до ручной правки firewall.

Теперь так:

* порт нашего UDP-транспорта (8450) открыт всем — иначе новый адрес не смог бы
  представиться;
* каждый пакет проверяется по HMAC (ключ только у нас) и по nonce (повторы
  отбрасываются — записанный провайдером пакет «проиграть» нельзя);
* первый же пакет с верной подписью запускает на сервере
  `netmon-whitelist <адрес>`: закрытые порты открываются **этому** адресу, не
  чаще раза в 5 минут, старые адреса убираются через 14 дней;
* клиенту ничего настраивать не нужно: keepalive каждые 15 с и повторы NMPT
  уже несут подпись.

Проверено вживую: пакет с постороннего адреса → через 3 секунды у него все
10 правил; адрес без правильной подписи не получает ничего.

Заодно TCP-путь перестал «карантиниться» из-за порчи рукопожатия: провайдер
подменяет байты в TLS, поэтому теперь делается до 4 попыток со свежим
соединением по всем портам релея, а карантин ставится только если не
устанавливается само соединение (режется SYN).

## Что нового в 3.20.1

**Клиент сам выбирает живой путь и больше не висит на мёртвом.**

Провайдер атакует волнами: утром он душит TCP (UDP идёт идеально), к вечеру
начинает резать UDP и портить часть TLS-рукопожатий. Раньше клиент каждый раз
пробовал NMPT первым и ждал 8 секунд, а потом падал на TCP — приложение получало
отказ, хотя второй путь работал.

Что сделано:

* **память о здоровье путей** — неудача на пути помечает его «мёртвым» на 60 с
  (UDP) или 30 с (TCP), весь трафик уходит на живой; если оба помечены — метки
  снимаются, чтобы связь не пропала совсем;
* **быстрый отказ**: открытие потока NMPT ждёт 2,5 с вместо 8;
* **гонка по нескольким портам релея**: `[tunnel] port_alt=8442,2083,2053,2087` —
  шесть попыток на каждый адрес; на сервере подняты дополнительные слушатели
  нашего же релея (2083, 2053, 2087), чтобы блокировка одного порта ничего не
  решала;
* **одно ядро на систему**: окно, сторож и CLI больше не могут запустить три
  процесса сразу (наблюдали 2–3 копии, которые дрались за порт SOCKS);
* **ядро поднимается при старте монитора**, а не только сторожем: если сторож
  выключен, после перезагрузки туннель всё равно включается;
* новая команда диагностики: `netmon.exe --cli core relay path` — проверяет оба
  пути и печатает, какой из них сейчас живой и что выберет ядро.

**Интерфейс перестал греть процессор.** Наблюдалось 75–80 % одного ядра в простое:
пересчёт попадания мыши вызывался 12 раз в секунду даже при неподвижном курсоре,
а свёрнутое окно продолжало считать раскладку. Теперь попадание считается только
при движении мыши (и раз в 0,5 с как страховка), свёрнутое окно не считает вовсе,
кадров анимации 6 вместо 12. Итог: **78 % → 23 %** ядра в простое.

Ещё: в `netmon.ini` был включён `tun_trace=1` — построчная трассировка каждого
пакета в журнал. Она давала мегабайты логов и заметную нагрузку; в поставке
выключена (`tun_trace=0`).

## Что нового в 3.20.0

**Сервер NMPT переписан на C++: скорость выросла в десятки раз, параллельные
загрузки больше не душат друг друга.**

Python-сервер упирался в одно ядро (83 % при нескольких загрузках), поэтому та же
логика перенесена на C++ (`tools/netmon_cpp/server_linux/nmpu_server.cpp`): epoll,
неблокирующие сокеты, батчевый приём пакетов, резолвер в отдельном потоке и
несколько воркеров (`fork` + `SO_REUSEPORT`). Протокол и крипто не менялись —
клиент совместим с обеими реализациями.

Заодно убраны три причины просадок:

* окно «в полёте» поднято (640 пакетов на поток на сервере, 256 на клиенте,
  1024 суммарно) — прежние 48 резали загрузку до 0,4 МБ/с;
* подтверждения не на каждый пакет, а на каждый четвёртый или через 6 мс, причём
  ACK не двигаются, пока приложение не разобрало буфер (обратное давление);
* повторы «мёртвых» потоков прекращаются: сервер закрывает поток после 8 попыток
  FIN, клиент отвечает `RST` на кадр неизвестного потока. Раньше эти повторы
  забивали сокет, и новые потоки вообще не открывались (рукопожатие висело 8 с).

Скорость: шифр переведён на AES-256-CTR (аппаратный AES-NI) с байтом версии в
пакете, окно «в полёте» поднято до 2 МБ, в пакете 1350 байт данных. Сервер сам
определяет шифр по пакету и отвечает тем же; клиент выбирает настройкой
`[tunnel] crypto=aes|sha` (`sha` — совместимость со старым сервером на Python).

Замеры на живом канале (провайдер душит TCP, UDP идёт чисто):

| Сценарий | Python-сервер | C++ + SHA-256 | C++ + AES-CTR |
| --- | --- | --- | --- |
| 40 МБ, один поток | 0,14 МБ/с | 5,0 МБ/с | **12,3 МБ/с** (98 Мбит/с) |
| 4 × 40 МБ параллельно | — | 6,3 МБ/с | **27,9 МБ/с** (223 Мбит/с) |
| 6 параллельных запросов | 1/6 скорости | 6 из 6 | 6 из 6, худший 0,6 с |

Один воркер держит ≈100 Мбит/с (упор в SHA-256 нашего шифрования), воркеров на
сервере — 4. Появился приёмочный замер из клиента:
`netmon.exe --cli core relay nmpt example.com:80 6` и
`netmon.exe --cli core relay nmpt <сервер>:8920 2 /file.bin`.

## Что нового в 3.19.0

**NMPT — надёжные потоки поверх нашего UDP: TCP больше не нужен.**

Провайдер душит TCP (рукопожатие к нашему серверу 3–17 секунд, прямой канал тоже
рвётся), а UDP до того же сервера идёт идеально (129 мс, 0 потерь). Поэтому поток
теперь несёт наш собственный надёжный протокол поверх нашего же UDP:

```
OPEN(sid, цель) | OPEN_OK / OPEN_ERR
DATA(sid, seq, данные)   — по 1100 байт
ACK(sid, следующий ожидаемый seq)
FIN(sid, seq) | RST(sid)
```

Своя нумерация, свои подтверждения, повторы по RTO (0,5 с), окно 48 пакетов на
поток и общий предел «в полёте», защита от повторов и шифрование — всё своё,
поверх NMPU (SHA-256 + HMAC на системных примитивах). Ни TCP, ни QUIC, ни чужих
библиотек в этом пути.

Замер в текущих условиях (провайдер душит TCP):

| Путь | Результат |
| --- | --- |
| 10 запросов подряд через NMPT | **10 из 10**, 1,49–1,71 с, стабильно |
| 16 разных сервисов через NMPT | 15 из 16, среднее 1,5 с |
| Обычный TLS-релей (было) | 3–17 с на рукопожатие, частые обрывы |

Заодно исправлено:

* **падения `c0000005` и порча кучи** — гонка владения потоковыми объектами:
  «отстойник» закрытых потоков хранил сырые указатели при владении через
  `shared_ptr`, из-за чего объект освобождался дважды. Теперь владение
  передаётся в отстойник целиком; 0 падений после правки.
* **деградация со временем** — мёртвые потоки продолжали слать повторы и душили
  сокет; добавлена уборка неактивных потоков и повтор FIN (одиночный FIN терялся,
  и приложение ждало вечно).

Известное ограничение: при большом числе одновременных загрузок (15+) наш
серверный разбор упирается в один поток Python. Очередной шаг — перенести
серверную часть NMPT на наш C++ (или разнести по нескольким воркерам).


**Свой UDP-транспорт (NMPU), обход «душения» портов и починка падений.**

Провайдер снова сменил тактику: TCP до нашего сервера стал местами по 3–17 секунд
(замер `core relay probe`: 2868, 9030, 3031, 16685, 17074 мс), при этом UDP до того
же сервера — идеально (129 мс, 0 потерь). То есть дело не в сервере и не в канале,
а в том, что провайдер душит именно TCP-соединения.

1. **NMPU — наш собственный UDP-транспорт для датаграмм.** Свой формат пакета,
   своё шифрование и аутентификация на системных хеш-примитивах (SHA-256 + HMAC,
   BCrypt на клиенте, hashlib на сервере), никаких чужих QUIC/TLS в этом пути:
   `nonce(8) | шифротекст | тег(16)`, ключи из общего секрета, защита от повторов.
   Проверка: `netmon.exe --cli core relay nmpu 20` → 20/20, 129 мс.
   Сервер: `server/netmon_nmpu.py`, служба `netmon-nmpu` на UDP 8450.

2. **Гонка портов.** Релей теперь слушает ещё и порт 8442 (`netmon-relay-alt`),
   а клиент пробует оба порта параллельно (`[tunnel] port_alt=8442`) — если
   провайдер душит один порт, второй работает.

3. **Починены падения (`c0000005` в `mutex_impl_init`).** Причина — гонка
   времени жизни: поток-насос мог ещё читать из соединения, когда объект уже
   освободили. Теперь закрытые соединения живут в «отстойнике» две минуты, а
   закрытие будит читателя, чтобы тот вышел сразу.

4. **Мультиплексирование NMR2 остаётся, но по умолчанию выключено** (`mux=0`):
   при текущем «душении» TCP одно долгое соединение страдает сильнее, чем
   короткие. Включается одной строкой, когда провайдер успокоится.

## Что нового в 3.13.7

Устранены причины, из-за которых рабочий режим сам «отваливался» в прямой.

  видимый адрес с сохранённым, проверяет SSH и сам синхронизирует вайтлист
  (один раз на адрес, не чаще раза в 10 минут). В журнале: «адрес 83.137.54.30
  авторизован на сервере».
* Авторизация открывает **все** входы — 443, 8388, 8443, 8444, 8447, 8448 (tcp,
  а где нужно и udp), — и не только текущий адрес, но и его подсеть `/24`:
  провайдер меняет адрес несколько раз в сутки внутри своей сети, поэтому
  точечное правило ломалось при следующей смене. Проверено: после авто-авторизации
  работают все 5 профилей (было 3), и смена адреса внутри подсети VPN не ломает.
* Новая страница **«Процессы» (Ctrl+8)**: роль, процесс, pid, память, время
  запуска, путь к журналу. Видны монитор, ядро (`core run`), предохранитель,
  сторож-задача, терминалы PowerShell и CMD, обновлятор, воркер саморазработки и
  все найденные потомки (`conhost`, `ssh`, `netsh` …). Щелчок по строке показывает
  вывод процесса во вкладке «консоль».
* CLI: `netmon.exe --cli procs` и `netmon.exe --cli procs log <pid>` — то же в тексте.
* Список чистится сам: короткоживущие роли хранятся одной записью, завершённые —
  только последние, поэтому минута за минутой список не разрастается.

## Что нового в 3.9.1

Всё выполняется во встроенных вкладках — окон на рабочем столе больше нет.

* Убрана главная причина всплывающих окон: `netmon.exe --cli` вызывал
  `AllocConsole()`, когда рядом не было консоли. Задача-сторож `netmon-proxy-guard`
  запускается раз в минуту — и каждый запуск создавал окно. Теперь при отсутствии
  консоли вывод идёт в `config\netmon\console.log` (виден во вкладке «консоль»),
  а окно не создаётся. Проверено приборным контролем окон: за 90 секунд с двумя
  запусками сторожа — 0 новых консольных окон.
* Вкладки терминала: **PowerShell** и **CMD** (палитра «Терминал: новая вкладка
  CMD/PowerShell»), у CMD своё приглашение `c:\путь>`.

  оставалась в состоянии «выполняется» (чтение псевдоконсоли блокировалось
  навсегда) — теперь чтение неблокирующее, завершение процесса определяется по
  его дескриптору, серия команд подряд работает.
* Кодировка вывода: `chcp 65001` и UTF-8 (pwsh при наличии), плюс выбор
  кодировки по содержимому строки — кириллица больше не превращается в «СЃРєСЂРёРїС‚».

* Внешние окна остаются только там, где это технически необходимо: редактор

Проверено: `netsh interface ipv4 show interfaces` и `netstat -an` внутри терминала

## Что нового в 3.8.0

Ключевое: **контроль пакетов на шлюзе и сторонних приложений**. Сеть проверяется не
только со стороны ПК, но и на сервере, а восстановление доводится до конца.

* `netcheck server` — состояние шлюза за окно 4 с: байты и пакеты, ошибки и дропы

## Что нового в 3.7.2

Ключевое: **сеть не пропадает никогда**. Раньше сторож проверял только «порт
открыт», а задача-сторож удалялась при выключении транспорта — после падения всех
процессов монитора сеть могла остаться с прокси на мёртвый порт. Теперь:

* Задача `netmon-proxy-guard` ставится при **каждом** старте монитора и не
  удаляется при выключении транспорта, поэтому сеть возвращается даже если
  монитор убили вместе с ядром (проверено: убийство всех процессов в режиме
  `proxy` → через 8 секунд ядро поднято, порт отвечает, монитор восстановлен).
* Сторож больше не полагается на счётчики в памяти (задача — новый процесс каждую
  минуту): подтверждение и решение принимаются внутри одного запуска.
* Новый модуль `netcheck`: реальные метрики (DNS, TCP, HTTPS, ICMP, джиттер,
  потери, внешний адрес, загрузка CPU), эталон **на каждый режим**, допуски с
  учётом шума и нагрузки, вердикт `ok/хуже`.
* После восстановления сети сторож проверяет метрики и при расхождении
  **откатывается** к обычному режиму и проверяет снова; в журналах
  `netcheck.log` и `transport-guard.log` видно, что именно было не так.
* `netcheck rivals` показывает, что ещё влияет на сеть: чужой WinHTTP-прокси,
  туннельные адаптеры в маршруте по умолчанию, сторонние клиенты, чужие задачи.
* `netcheck speed` — короткий замер скорости (2 МБ в текущем режиме): «страница
  открылась» и «канал работает» — разные вещи (проверено: 119 Мбит/с напрямую,
  10.5 Мбит/с через ядро).
* CLI и GUI дублируют друг друга: `netcheck [baseline|verify|rivals|speed]` и карточка
  «Качество сети» на странице «Подключение» (Ctrl+6) с кнопками «Проверить
  метрики» и «Сделать эталоном»; в самодиагностике появилась проверка `netcheck`.

## Что нового в 3.0.0

Ключевое: **свой VPN вместо чужого клиента**. Монитор поднимает штатное
подключение Windows (`WAN Miniport (SSTP)`) через RAS API — сторонние клиенты и
драйверы больше не нужны, весь трафик, включая UDP, идёт в туннель.

* Серверная половина — наш собственный эндпоинт `server/netmon_sstp.py`:
  TLS → HTTP `SSTP_DUPLEX_POST` → кадры SSTP (бит `C`, Crypto Binding с nonce и
  SHA-256 сертификата) → PPP (LCP, CHAP-MD5, IPCP) → Linux TUN + NAT.
* Клиентская половина — `vpn.cpp` на `rasapi32`: создание подключения
  (`RasSetEntryProperties`), учётные данные, `RasDial`, `RasHangUp`,
  `RasDeleteEntry`, доверие сертификату, `vpn repair` для ошибки 756.
* Новая проверка «Встроенный VPN» и кнопки подключения/отключения/починки в
  карточке проверки.
* Поддержан `WAN Miniport (SSTP)` как TUN-адаптер: маршрут по умолчанию идёт
  через туннель, локальная сеть остаётся доступной.

Проверено на живой Windows 11: `vpn on` → `10.77.0.3`, `curl https://api.ipify.org`
без прокси отдаёт адрес сервера, DNS и UDP идут через туннель, а с процессами
прежнего клиента, остановленными, интернет продолжает работать — то есть замещение
действительно полное. Версия базы знаний: статья «Встроенный VPN без сторонних
клиентов».

## Обновления

Клиент сам проверяет `manifest.json` (режим `update_mode` в `netmon.ini`):

```powershell
netmon.exe --cli update check     # есть ли новая версия
netmon.exe --cli update apply     # скачать, проверить SHA-256, подменить и перезапуститься
netmon.exe --cli self             # версия, права, автозапуск, журнал
```

Версия задана в одном месте исходников (`src\version.h`), поэтому манифест и клиент
всегда согласованы: `publish.ps1` берёт номер из `netmon.exe --cli self`.

## Сборка и публикация

```powershell
powershell -ExecutionPolicy Bypass -File .\publish.ps1 -Version 2.5.2 -Push
```

`publish.ps1` копирует свежий `netmon.exe` в `public/`, считает SHA-256,
переписывает `manifest.json` и делает коммит; с `-Push` отправляет в GitHub.
